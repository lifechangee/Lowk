# Связка ключей: почему macOS спрашивает доступ и как это убрать

## Почему появляются запросы

Ключи API лежат в login-связке (сервис `dev.lowk.app`, аккаунт = провайдер). У каждой записи есть ACL:
список программ, которым можно читать без вопроса. Программа в списке определяется её подписью.

1. **Пересборка меняет подпись.** Ad-hoc подпись привязана к хешу кода (cdhash), он новый при каждой
   сборке. Для macOS это другая программа, «Всегда разрешать» от прошлой сборки не действует.
2. **«Разрешить» вместо «Всегда разрешать».** Разовое разрешение живёт до конца процесса; каждое
   следующее чтение спросит снова.
3. **Много чтений.** Раньше ключ читался на каждый Ask, сводку, пробу и прогрев. Теперь (этот пакет)
   каждый ключ читается из связки не чаще одного раза за запуск и держится в памяти (zeroize), кэш
   сбрасывается при сохранении и удалении. Читает только основной процесс приложения. Тест
   `reads_keychain_once_per_run` считает реальные чтения.

## Для разработки: постоянная доверенная подпись

Сертификат «Lowk Dev» (см. `docs/setup/macos-signing.md`) даёт стабильное «designated requirement»,
поэтому ACL связки и разрешения TCC (микрофон, запись экрана и т.д.) переживают пересборки.

Чтобы macOS считал сертификат доверенным для подписи кода:

1. Связка ключей → связка «Вход» → раздел «Сертификаты» → дважды щёлкните «Lowk Dev».
2. Раскройте «Доверие» (Trust).
3. «При использовании этого сертификата»: **Всегда доверять** (или только в строке «Подпись кода»
   выберите «Всегда доверять»). Закройте окно, введите пароль пользователя.
4. Проверьте: `security find-identity -v -p codesigning` показывает «Lowk Dev» без пометки
   `CSSMERR_TP_NOT_TRUSTED`.
5. Пересоберите: `LOWK_SIGN_IDENTITY="Lowk Dev" just build`.

Дальше: при первом запросе нажмите **«Всегда разрешать»** (не «Разрешить»). Пока сертификат не
настроен, всё равно жмите «Всегда разрешать», это сократит число вопросов до одного на сборку.

Побочный эффект: доверенная стабильная подпись так же снимает сбросы TCC.

## Релиз

- **Developer ID** (Team ID): подпись стабильна между версиями, доступ к связке и TCC переживают
  обновления; для нотаризации нужен платный аккаунт Apple Developer.
- Рассмотреть **data-protection keychain** (kSecUseDataProtectionKeychain) с access group по Team ID:
  записи привязаны к команде, а не к ACL конкретной программы, запросов нет совсем. Требует
  provisioning profile с entitlement `keychain-access-groups`; пакет доступен только для подписанного
  Developer ID приложения.

## Windows

Credential Manager привязан к учётной записи пользователя, запросов нет.

## Зашифрованный файл вместо связки (для полноты, не рекомендуется)

Плюсы: нет запросов. Минусы: ключ шифрования придётся хранить рядом (тогда это обфускация) или спрашивать
пароль у пользователя; нет защиты ОС от чтения другими программами, нет синхронизации с политиками
связки. Для API-ключей стандартный путь надёжнее.

## Что не сделано

Автоматическая запись ACL (SecAccess / partition list с designated requirement) при сохранении
ключа: `keyring` не даёт этого API, а прямой вызов `SecAccessCreate`/`SecKeychainItemSetAccess`
ненадёжен (устарел, поведение зависит от версии macOS). Решение через стабильную подпись выше
покрывает ту же задачу.
