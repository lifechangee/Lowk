# Синхронизация между устройствами и шифрование хранилища

Статус: дизайн-ресёрч, 2026-10-22. Опирается на ARCHITECTURE §4 (vault: Markdown + `.lowk/index.db`, ULID в frontmatter, индекс перестраиваемый, `settings.toml`/секреты/модели не в vault).

## 1. Что синхронизируем

| Что | Синкать? | Примечание |
|---|---|---|
| `*.md` (звонки, `_folder.md`), документы, `.assets/` | да | источник истины |
| `.lowk/index.db` (SQLite, FTS5, векторы) | **нет** | перестраиваемый, бинарный, конфликтует; на каждом устройстве свой |
| `.lowk/trash/` | да (по возможности) | чтобы удаление на одном устройстве было восстановимо на другом |
| `.lowk/state/live/*` (журналы звонков) | нет | локальные, для восстановления после падения |
| `settings.toml`, секреты, модели, логи | нет | машинно-зависимые (уже вне vault) |

Следствие: **синхронизируется только то, что и так Obsidian-совместимо.** Это даёт нулевую зависимость от собственного бэкенда.

## 2. Варианты

### A. Папка vault в стороннем синхронизаторе (iCloud Drive / Dropbox / OneDrive / Syncthing / Google Drive)
- Пользователь кладёт vault в синхронизируемую папку. Lowk ничего не знает о сети.
- Что нужно от Lowk (небольшая работа):
  1. Исключить `.lowk/index.db*` из синка: iCloud - суффикс `.nosync`/каталог `index.db.nosync` с симлинком; Dropbox - `xattr com.dropbox.ignored` / `Set-Content -Stream com.dropbox.ignored`; Syncthing - `.stignore`; OneDrive - не исключить (хранить индекс вне vault: `<app data>/index/<vault-id>.db`). **Рекомендация: хранить индекс всегда вне vault** при включённом режиме синка (путь от vault-id в `.lowk/vault.json`).
  2. Корректно переживать появление/исчезновение файлов «снизу»: watcher (`notify`) + хэш-реестр собственных записей уже предусмотрены (ARCHITECTURE §4.1); дописать «файл-заглушка» iCloud (`.name.md.icloud`, оффлайн-выгрузка) - показывать «загружается», не считать удалением.
  3. Конфликтные копии (`file (conflicted copy).md`, `file.sync-conflict-*.md`, iCloud `file 2.md`) - распознавать и показывать диалог слияния (§3).
  4. Блокировки и атомарность записи: temp + rename (уже в `lowk-store`), не держать файл открытым; не писать живой журнал звонка в vault (он в `.lowk/state` - исключить).
- Плюсы: ничего не хостим, E2E-шифрование зависит от провайдера (Syncthing - да, Dropbox/iCloud - частично), юридически нейтрально. Минусы: нет гарантий порядка/конфликтов, живая запись звонка на двух устройствах одновременно - редкий кейс, обрабатываем конфликтом.
- Эффорт: 2-3 WP.

### B. Git-синхронизация
- `.lowk/` в `.gitignore`; Lowk выполняет `commit`+`pull --rebase`+`push` по расписанию/событию (крейт `gix` или вызов системного `git`).
- Плюсы: история и диффы по .md бесплатно, трёхстороннее слияние текста, любой хостинг (GitHub private, Gitea, Forgejo). Минусы: бинарные документы/assets раздувают репо (LFS); нужен git и ключи/токены - для нетехнического владельца тяжело; приватные данные созвонов на GitHub - вопрос доверия (шифрование нужно до push).
- Эффорт: 4-5 WP, рекомендовать как опцию для продвинутых, не по умолчанию.

### C. Свой сервер / self-hosted
- Минимальный вариант: WebDAV/S3-совместимое хранилище (MinIO, Nextcloud) + клиент в Lowk, синхронизирующий файлы по ETag/хэшу; либо готовый CRDT/sync-слой.
- Плюсы: контроль, E2E по-нашему. Минусы: пишем и поддерживаем протокол, аутентификацию, дисковые квоты, безопасность - самое дорогое. Противоречит минимализму (телеметрии нет, облака нет).
- Эффорт: 10+ WP, откладывать до явного спроса.

### Рекомендация
1. **Фаза 1:** вариант A как документированный и поддержанный сценарий (индекс вне vault, распознавание конфликтных копий, «заглушки» облака).
2. **Фаза 2:** шифрование (§4) - чтобы A безопасно работал через любой облачный диск.
3. **Фаза 3 (по спросу):** git-режим для продвинутых; C - не планируем.

## 3. Конфликты

Единицы конфликта - файл. Файлы звонков в основном append-only после окончания звонка, поэтому конфликты редки; чаще правки заметок, `_folder.md`, переименования.
- Идентичность по `id` (ULID) во frontmatter, а не по пути (ARCHITECTURE §4.1): переименование на A и правка на B сводятся автоматически, если watcher видит «тот же id, новый путь».
- **Обнаружение:** (а) конфликтные копии по шаблонам имён; (б) два файла с одним `id` в vault; (в) при записи: сравнить `blake3` с последним известным (optimistic concurrency) - если на диске иной, не перезаписывать, сохранять как `...conflict-<device>-<ts>.md`.
- **Слияние:** 3-way merge по тексту (база = последняя версия, которую видели оба; хранить в `.lowk/merge-base/<id>` или брать из trash/журнала) крейтом `diffy`/`similar`; frontmatter сливать по ключам (последнее изменение выигрывает по полю, `tags` - объединение). Неразрешимое - диалог «оставить мою / их / обе (две вставки с маркерами)». Никогда не терять данные: в худшем случае остаются обе копии.
- Структура файла звонка (Speaker-реплики с таймкодами) облегчает слияние: реплики - строки, добавления разных устройств не пересекаются.
- Удаление vs правка: «правка побеждает удаление» (восстановить из trash).
- **Индекс:** конфликтов нет (локальный), после применения изменений - инкрементальная переиндексация по хэшам; при чужом большом обновлении - фоновая реиндексация с прогрессом. Эмбеддинги: модель должна быть одинакова на устройствах, иначе поиск работает независимо (индекс не синкается, поэтому не критично).

## 4. Шифрование хранилища паролем (пункт роадмапа)

Цели: защита от потери устройства и от облака-хранилища (вариант A/B). Не цели: защита от malware на включённом разблокированном устройстве.

### Подходы
1. **Шифрование диска ОС** (FileVault/BitLocker) - уже есть; не защищает от облачного провайдера. Рекомендовать в онбординге, не заменяет.
2. **Файловое шифрование внутри vault** (рекомендуется): каждый `.md` и asset хранится как зашифрованный контейнер, расширение `.md.lowk` (или `.md.age`). Минус: Obsidian-совместимость теряется для зашифрованного vault (ясно сообщить; выбор при создании vault: «Открытый (Obsidian)» / «Зашифрованный»).
   - Крипто: `age` (rage, формат с scrypt-рецепиентом: пароль -> ключ) или собственная схема XChaCha20-Poly1305 с ключом из Argon2id(пароль, соль, m=64MiB, t=3). Рекомендация: **использовать готовый формат age**: аудитированный, есть крейт `rage`/`age`, CLI для аварийного расшифрования без Lowk.
   - Ключ шифрования данных (DEK, случайный 256 бит) шифруется ключом из пароля (KEK, Argon2id) и хранится в `.lowk/keys.json` (вне зашифрованных файлов, синкается: позволяет сменить пароль без перешифровки). Опционально - второй KEK: ключ восстановления (печатается пользователем).
   - Разблокировка: пароль при запуске; DEK кладём в OS keychain на время сессии (по желанию «запомнить на этом устройстве», защищено биометрией).
3. **Прозрачное шифрование индекса:** SQLCipher или шифрование `index.db` тем же DEK; проще и надёжнее - **индекс только в памяти/в app data устройства** (ОС-шифрование) и пересобираемый, но он содержит открытый текст (FTS) -> нужен SQLCipher (`rusqlite` feature `bundled-sqlcipher`) либо хранить индекс на зашифрованном томе. Решение: SQLCipher, ключ = производный от DEK. Цена - потеря `sqlite-vec` вместе с SQLCipher проверить (совместимость расширений) [проверить].
4. **Имена файлов и frontmatter:** при шифровании имён поиск по папкам в облаке невозможен; компромисс: имена в открытом виде (удобство) или хэшированные (приватность) - вопрос владельцу.

### Влияние на другие модули
- LLM-контекст: расшифровка при чтении, в память; телеметрии нет.
- Watcher: события на `.md.lowk`, расшифровка в `lowk-store` слое (кодек), остальные крейты видят открытый текст через `Vault`.
- Миграция существующего vault: фоновый «зашифровать всё» с журналом, откат. Обязательный бэкап перед запуском.
- Аудио (если сохраняется): тоже шифруется.
- Забытый пароль = потеря данных; честное предупреждение + ключ восстановления.

Эффорт: 5-6 WP (кодек и ключи 2, миграция 1, SQLCipher/индекс 1-2, UI и разблокировка 1, тесты и модель угроз 1).

## 6. Риски
- iCloud «Оптимизация хранилища» выгружает файлы - индексатор не должен считать их отсутствующими.
- Синхронизаторы и SQLite WAL-файлы - повреждение индекса (поэтому индекс вне vault).
- Часы устройств расходятся - сравнивать хэши и id, а не mtime.
- Windows: ограничение длины пути (`\\?\` уже предусмотрено), регистр имён между macOS/Windows (коллизии `A.md`/`a.md` - обнаруживать).
- Несовместимость разных версий Lowk на устройствах: `lowk: 1` во frontmatter - версионирование схемы; новее версия формата -> read-only.

2. Какой облачный сервис реально используется (iCloud/Dropbox/Syncthing/другой)? От него зависят детали исключений.
3. Шифрование: готовы ли терять Obsidian-совместимость зашифрованного vault? Имена файлов прятать или нет?
4. Ключ восстановления - да/нет (иначе забытый пароль = потеря данных)?
5. Нужен ли git-режим вообще?
