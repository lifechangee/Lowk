# Роадмап: диаризация потока «Система» («Собеседник 1/2/…»)

Статус: ресёрч + прототип на файлах (22.10.2026). Код и сырые результаты: `spikes/diarization/`.
Контекст: `docs/BRIEF.md`, `docs/ARCHITECTURE.md` §6, `docs/DECISIONS-M1.md`, `spikes/stt-bench/RESULTS.md`.

## 1. Рекомендация (коротко)

**Локально: NVIDIA Nemotron-3-Diarization (GGUF Q8_0, 107 МБ) через NeMo-Speech.cpp (Apache-2.0, ggml) в отдельном sidecar-процессе
`lowk-diar-worker`.** Один тот же класс моделей и та же лицензия (OpenMDW-1.1), что у уже выбранного Nemotron-ASR; тот же ggml-стек
(Metal на macOS, Vulkan/CPU на Windows), без Python. Стриминговая модель: задержка 0,32 / 0,64 / 1,04 с на выбор, до 8 говорящих,
идентификаторы стабильны (порядок первого появления), не нужен онлайн-кластеризатор.

Что получаем на наших файлах (раздел 3): реальные разные голоса (6 дикторов FLEURS-ru, 110-340 с, с перебиваниями) —
**DER 0,3-4,4 % (ggml Q8_0, Metal), число говорящих определено верно во всех 4 сценариях (2/3/4/6)**; в потоковом режиме
с задержкой 0,32 с — 4-9 % (из них 4-5 % это «пропуски» из-за неточной VAD-разметки эталона, путаницы 0-5 %).
Скорость: RTF 0,04 (Metal, весь файл включая загрузку модели), 0,14-0,29 (только CPU, M4); RAM процесса ~350 МБ.

Дополнительно (поздние этапы): (а) облачный адаптер — поле `speaker` у токенов Soniox/Deepgram как альтернативный источник
тех же меток; (б) «запомнить голос» — отдельный маленький эмбеддер (3D-Speaker ERes2Net ~40 МБ или TitaNet-small ~40 МБ):
на наших данных 100 % верных опознаний по одному 10-20-секундному образцу (40 реплик, 6 дикторов).

**Чего НЕ делаем:** pyannote/diart (токен HF + gated-репозиторий, нет готового Rust/ggml-рантайма, потоково слабее),
Sortformer 4spk v2/v2.1 (лимит 4 говорящих, лицензия NVIDIA Open Model License, заметно хуже Nemotron-3), кластеризацию
эмбеддингов поверх sherpa-onnx как основной движок (оффлайн, без известного N ломается, см. ниже).

## 3. Прототип на файлах (тихо, без звука)

### 3.1 Данные и честные оговорки

* Записи владельца: `*_me_*` и `*_them_*` оказались **одним голосом** (косинус эмбеддингов 0,7-0,9 для обеих пар, как внутри
  одного диктора; две независимые модели). Поэтому сценарии `s1-s4` (владелец, «партнёр», `say` Milena, питч-сдвиг) на деле
  проверяют «не склеивает ли модель один голос с самим собой» и дают заведомо плохой DER (27-39 %): обе системы честно считают
  это одним человеком. Сдвиг питча на +4 полутона голос не меняет (модели правильно считают его тем же голосом).
  Для реального теста **нужны записи с настоящим вторым человеком** (попросить владельца: 3-минутный разговор втроём).
* Основной тест: **FLEURS ru_ru dev** (Google, CC-BY-4.0, 356 высказываний). Идентификаторов дикторов в наборе нет;
  восстановлены псевдо-дикторы агломеративной кластеризацией TitaNet-small (ни одна из тестируемых систем TitaNet не использует):
  7 кластеров ≥5 высказываний, внутри кластера пол одинаков (3 жен., 3 муж. взяты в тест). Из 3-15-секундных высказываний
  собраны диалоги с перебиваниями (12-20 % реплик начинаются поверх предыдущей), 110-343 с. **Это чтение вслух по бумаге, а не
  живая речь**: эмоций, «угу», фонового шума и сильных перекрытий меньше, чем в созвоне; реальный DER будет хуже.
* Эталон: энергетическая VAD по каждому исходному клипу до сборки (кадр 30 мс, пауза >0,45 с склеивает), поэтому границы
  грубые; DER с «collar» 0,25 с, перекрытия учитываются, сопоставление говорящих венгерским алгоритмом.

* Разница столбцов «ggml» и «Transformers»: в Transformers-прогоне мой собственный пост-процессинг (порог 0,5, минимум 0,2 с,
  без паддинга) и принудительная раздельная обработка кусков; почти вся разница в «пропусках» (miss 3,8-5,2 %), а не в путанице
  (conf 0-5 %). В продукте пост-процессинг будет наш (гистерезис, паддинг), рабочая цифра ожидаемого качества на чтении - 1-5 %.
* Задержка метки: модель ждёт 0,32 / 1,04 с аудио до разметки чанка; вычисление чанка на CPU в PyTorch (идёт параллельно с
  другими прогонами, не продуктовый рантайм) p50 108-219 мс (0,32 с) и 182-399 мс (1,04 с), p95 до 0,6 с.
  Итог «речь произнесена → метка готова» ~0,5-0,9 с (0,32 с) и ~1,3-1,6 с (1,04 с). В продукте считает ggml на Metal: RTF 0,04.
* Производительность ggml-рантайма на M4 (веса Q8_0; файл целиком, включая загрузку модели ~0,3 с): Metal RTF 0,04-0,05,
  только CPU RTF 0,14-0,29, RAM пик 350 МБ. Windows (Vulkan/CPU) **не измерялась**, прикидка по CPU-цифре.
* Точность при ≥5 говорящих у NVIDIA заметно падает (5-9 говорящих: ~27,6 % на их корпусе); в звонках обычно 2-5.
* Вывод про sherpa-onnx: при известном числе говорящих оффлайн-пайплайн так же точен, но (а) число в реальном звонке неизвестно
  (порог не переносится между записями), (б) нет потокового режима: пересчёт растущего окна O(n), метки прошлого пересчитываются,
  (в) сегментация pyannote-3.0 ограничена окном 10 с. Рекомендация: sherpa/ort только для эмбеддингов голосов.
* Опознание по голосу (enrollment): образец 10-20 с из другого высказывания, нужное лицо находится среди 6 для 40 из 40
  реплик ≥2 с (3D-Speaker, WeSpeaker, TitaNet; запас косинуса между лучшим и вторым p50 0,40 / 0,19 / 0,41; p10 0,27 / 0,11 / 0,29).
  Лучший по запасу и по лицензии - 3D-Speaker ERes2Net (Apache-2.0). Оговорка: те же 6 «дикторов» и тот же язык, коротких перекрытий и
  разной аппаратуры у одного человека (ноутбук/телефон/гарнитура) в тесте нет.

`run_nemocpp.py` / `run_nemotron3.py` / `run_sherpa.py` / `enroll_test.py`; DER: `der.py`. Сырые JSON: `spikes/diarization/results_*.json`.

## 4. Архитектура

### 4.1 Место в конвейере

```
lowk-audio  (Frame16k, stream=System, непрерывное время по часам)
   ├──► lowk-stt  (System worker)  ──► SttEvent{utt, rev, text, t_start_ns, t_audio_end_ns}
   └──► lowk-diar (НОВЫЙ, 2-й потребитель того же потока)
            └─ sidecar lowk-diar-worker  (NeMo-Speech.cpp: stream_open / push_f32 → вероятности кадров 10 мс × 8)
            └─ пост-процессинг (гистерезис, мин. длительность)  ──► SpeakerSpan{t0_ns, t1_ns, spk 0..7, final}
lowk-session:  SpeakerTimeline (append-only) + Binder ──► TranscriptBuf (поле speaker у строки) ──► шина событий
Me-поток: диаризации нет, всегда «Я».
```

* Sidecar, а не библиотека в процессе: тот же аргумент, что в DECISIONS-M1 §1 (изоляция падений, ggml двух разных рантаймов -
  transcribe.cpp и NeMo-Speech.cpp - в одном процессе конфликтует по символам). Воркер вне workspace-членов, как `lowk-stt-worker`,
  собирается `tools/build-worker.sh`-подобным скриптом; рассмотреть вариант «взять готовый релиз NeMo-Speech.cpp по закреплённому
  SHA» (macOS Metal 5 МБ, Windows Vulkan 19 МБ) и тонкую Rust-обёртку над `diar.h`, чтобы CI не требовал CMake для этого воркера.
  Воркер бандлится в приложение (≈ 6-10 МБ), модель 107 МБ скачивается по запросу через `ModelStore` (SHA-256 закреплён,
  лицензия OpenMDW-1.1 показывается до скачивания, `EngineInfo.license_url`).
* Протокол воркера: stdin - PCM f32 16 кГц + метка `t_mono_ns` первого кадра; stdout - строки JSON `{frame0, probs:[8]}` пачками
  по чанку; команды `flush`/`stop`. Пост-процессинг в Rust (`lowk-diar`), а не в воркере: порог/гистерезис настраиваются и
  тестируются без пересборки C++.
* Привязка времени: индекс кадра → `t_mono_ns` через `t_mono_ns` первого кадра (на Windows Frame16k уже заполняется нулями по часам,
  ARCH 6.1, поэтому непрерывность сохраняется; пауза/потеря кадров - счётчик `Dropped` сдвигает кадровую сетку).
* Режим задержки по умолчанию - 0,64 с (`very_low_latency`): прирост от 1,04 → 0,32 с на наших данных ≤0,6 п.п. DER, но чанки в 3
  раза чаще; окончательно выбирается по замеру на Windows. Профиль - одна строка настройки (как `LocalTuning` в STT).
* Бэкпрешер: воркер не успевает (backlog > 3 с) → дропаем самые старые кадры, метка `unknown` на дыру, счётчик в диагностике;
  `SidecarEngine`-подобный рестарт 3 раза, затем «диаризация недоступна» без влияния на транскрипт и оверлей.
* Не в транскрипционном воркере: у STT-воркера свой ggml и бюджет RAM (~1 ГБ на поток); диаризация добавляет ~0,35 ГБ только на время звонка.
  Холодный старт - как у STT (загрузка при Record, прогрев `warm` после запуска приложения, тот же гейт по свободной памяти).

### 4.2 Как метки попадают в строки транскрипта и пересматриваются

Данные (расширение `lowk-types`, без ломки старых файлов):
* `SpeakerId` - стабильный идентификатор внутри звонка (`s1..s8`, соответствует индексу канала модели; «я» - отдельный `me`).
* `TranscriptLine.speaker: Option<SpeakerRef { id, rev, source: Auto|User }>`.
* Событие `transcript://speaker {seq, speaker, rev}` (шина уже умеет патчить строки по `seq`, ARCH `TranscriptBuf`).

Привязка (Binder в `lowk-session`):
1. Окно строки: `[t_start_ns, t_audio_end_ns]` System-реплики.
2. Для окна считаем время речи по каждому говорящему из `SpeakerTimeline`; метка = говорящий с долей ≥ 60 % речи окна;
   иначе - «смешанная» (см. 3). Нет речи в окне → `None` (строка остаётся «Система»).
3. Если вторая доля ≥ 1,2 с и ≥ 25 % → реплика **делится**: нужны границы по словам. У live-Nemotron слов-времён нет;
   их даёт коррекционный проход Whisper (ревизия `rev n+2`, токен-таймстампы) → строка делится на дочерние `UttId` по смене
   говорящего (`TranscriptBuf::split(seq, [(char_range, speaker)])`, новые `seq` вставляются после родителя; Ask-снапшот
   видит обновлённую картину как сейчас). До появления Whisper-ревизии (или если коррекция выключена/пропущена) - метка большинства
   (WP6 в плане; MVP без деления).
4. Метка приходит позже финала: финал появляется через ~0,14 с после конца речи + 480 мс hangover VAD, метка через 0,5-1,6 с.
   Поэтому строка сначала выходит как «Система» (или с меткой «предварительно» для активного говорящего, пока говорит) и
   **получает метку патчем**; повторных перескоков не ожидается, потому что стриминговый Sortformer не переписывает уже
   выданные кадры (метки стабильны по порядку первого появления). Пересмотр возможен только (а) делением по 3,
   (б) действием пользователя. Метки пользователя (`source: User`) всегда сильнее авто-меток.
5. Партиалы: метка активного на текущий момент говорящего, показываем только после подтверждения (≥0,5 с речи), без дёргания.
6. Лента звонка: «Собеседник N» показывается только после того, как обнаружен второй говорящий с ≥2 с речи (один человек
   - остаётся «Система», как сейчас). Настройка: «Авто / Всегда / Выключено».
7. Журнал звонка (`.md`): `[00:00:21] **Собеседник 1:** …`; таблица `speakers` во frontmatter расширяется
   (`system: "Система"`, `s1: "Собеседник 1"`, `s2: "Пётр"`, …), переименование = правка одной записи таблицы, тексты строк не
   трогаем (ARCH 4.2 уже допускает неизвестные метки как «дополнительные»). Ручные склейки пишутся как алиасы `s3: s1`.
   Ask/LLM-контекст получает метки автоматически (в дельте: `Собеседник 1: …`), что для ответов LLM полезнее, чем «Система».

### 4.3 Идентичность и «имя из голоса» (поздний этап)

* Профили: `<app data>/voices/<id>.json` = имя + 1-5 эмбеддингов (192-256 float), без аудио; только локально, не синхронизируется,
  не попадает в экспорт vault; кнопка «удалить все голоса» в настройках. Это биометрия (GDPR ст. 9): явное согласие при первом
  сохранении, текст в онбординге/README.
* Эмбеддер: 3D-Speaker ERes2Net (Apache-2.0, 40 МБ ONNX) через `ort` в том же `lowk-diar-worker` (второй режим, `embed`).
  Не использовать как есть WeSpeaker/TitaNet в продукте до проверки лицензии обучающих данных (VoxCeleb).
* Сбор: для каждого говорящего копим эмбеддинги из «чистых» участков (без перекрытия, ≥2 с, до 10 штук, усреднение);
  сравнение с профилями по косинусу: порог 0,45 и запас ≥0,15 над вторым → подсказка «Похоже на Пётр? [Да] [Нет]»,
  автоматически без подтверждения не применяем (первые 2 раза). «Запомнить голос» - из меню чипа говорящего, без отдельной
  процедуры записи.

### 4.4 Облачный режим

Если выбран Soniox/Deepgram, адаптер маппит `speaker` токена/слова на `SpeakerId` напрямую (деление по словам бесплатно,
токены уже имеют метки); локальная диаризация при этом выключена по умолчанию (иначе двойная нагрузка и два разных мнения).
Метки Soniox в реальном времени могут переключаться (документация), поэтому событие `transcript://speaker` с `rev` нужно именно здесь.
Soniox на нашем аккаунте не проверялся (баланс 0, DECISIONS-M1 §4), так что формат ответа с диаризацией проверить отдельно.

## 5. UX

* **Чип говорящего** слева от строки в окне звонка: «Собеседник 1», цвет из набора (в оверлее - только текст, стелс-палитра
  монохромная, ARCH 2.2). Первые 2 секунды нового чипа - без подчёркивания «не подтверждён».
* **Переименование**: клик по чипу → поповер: имя (автодополнение из сохранённых голосов и участников встречи, если календарь
  когда-нибудь подключим), «Запомнить голос» (поздний этап), «Применить ко всем строкам» (по умолчанию да). Переименование
  меняет таблицу `speakers`, а не тексты; в `.md` и в поиске отображается новое имя; Undo.
* **Склеить**: «Это тот же человек, что …» (выбор из списка говорящих): алиас, не пересчёт; нужно для случая «модель разделила
  одного человека на двух» (смена микрофона, шум) - самая частая ошибка диаризации.
* **Разделить / переназначить**: на строке меню «Сказал другой человек» → выбрать существующего или «новый»; пометка `User`
  фиксируется и не перезаписывается моделью. Деление длинной реплики по границе слов - после WP6.
* **Пересчитать говорящих** после звонка: офлайн-проход `v3-offline` (DIHARD III 12,7 против 13,2 % потоково - выигрыш
  небольшой) возможен только если аудио звонка сохранено; в альфе аудио не хранится, поэтому это не обязательство.
* **Индикаторы**: в оверлее при ≥2 говорящих - имя активного говорящего у верхней строки; ничего лишнего, пока говорящий один.
  Ошибка воркера - обычная плашка «диаризация недоступна», транскрипт работает.
* **Настройки** (Транскрипция → Говорящие): режим Авто/Всегда/Выкл; максимум говорящих (по умолчанию 8); профиль задержки (Баланс/Быстрее);
  локальная/облачная; «Голоса» (список профилей, удалить).
* Ask-шаблоны и «Мой ответ»: дельта для LLM содержит «Собеседник 1:»; захват «Мой ответ» по-прежнему по потоку Me.
