## Round 3: AirPods / Bluetooth and keyboard layout (2026-10-21, owner's real setup: AirPods Pro as default output AND mic, input source «Ру»)

| ID | Status | Root cause / numbers | Permanent check |
|---|---|---|---|
| A | fixed (System stream); verification with sound see below | With a Bluetooth headset the aggregate device behind the process tap runs at the HFP rate (24 kHz; 16 kHz on some headsets) once the microphone is open, but `kAudioTapPropertyFormat` keeps reporting the output's nominal 48 kHz. We trusted the tap format, so System audio was resampled as 48 kHz: everything 2x too fast (pitch up one octave, half the duration), i.e. unrecognisable. Measured on this Mac with silent `afplay -v 0`: 24 kHz aggregate, tap says 48 kHz; System audio before = 3.44 s for ~6.7 s of capture, after = 7.98 s for ~8 s. The call in the log (`sources: system: 47096`) also never started a tap at all: the pid the owner/orchestrator picked was not the process making sound (a launcher/shell around `afplay`; no audio process object, so `TargetLost` after 3 s and no tap for the whole call). A pid target now also resolves to its descendants that have an audio process object. The mic path (24 kHz, mono) was fine at the library level (8.36 s for 8 s); a headset that flips profile after the IOProc started would have made the same rate mistake, so the supervisor now restarts the mic when `actual_sample_rate` moves, and rebuilds the tap on aggregate-rate change (A2DP <-> HFP). Zero Me lines in that call = nobody spoke into the mic (afplay played into the AirPods, not the mic). | `tap::delivered_rate` tests; pipeline `device_matrix_rates_keep_duration_and_pitch` (16/24/32/44.1/48/96 kHz: duration and 440 Hz tone intact), `rate_flip_a2dp_to_hfp_and_back_keeps_time`; `procs::pid_spec_reaches_the_child_that_makes_sound`. Not coverable in `qa-bundle` without playing sound; real sound, AirPods HFP (owner-approved 4 s tone at -v 0.15): System capture 8.10 s for 8 s, energy at 440 Hz (880 Hz = 0), i.e. pitch and duration correct. |
| B | not a Lowk bug (layout independent), regression check added | Binds match the PHYSICAL key (`CGEventGetIntegerValueField(keycode)` -> kVK table), never characters. Proved with real HID events (`CGEventPost`, kVK 1 / kVK 0 with ⌘⇧) into the running bundle under RussianWin and ABC: ⌘⇧S key -> `Screenshot`, ⌘⇧A key -> `ScreenshotArea` in both layouts. `ScreenshotArea` on «⌘⇧S» came from character-based key injection (computer-use `key cmd+shift+s`): with «Ру» active there is no "s" character, so the injector picks another physical key.
